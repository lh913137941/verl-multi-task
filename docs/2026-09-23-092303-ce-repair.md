## 原生依据与设计歧义

`verl/checkpoint_engine/base.py` 的 `build_process_group` 使用传入的 rollout worker group；
`update_weights` 则遍历全部 `self.replicas`，并执行全体 abort/KV 操作。
因此 pending ADD 不能提前加入该列表。`add_replicas` / `remove_replicas` 只改变列表，
不会立即重建通信组。`nccl_checkpoint_engine.py` 和 `hccl_checkpoint_engine.py`
的构造默认关闭 rebuild，finalize 仅在该选项为真时销毁通信组。

092303 §8.6 同时写了“装参成功后才更新 E”和“目标必须是 E 的子集”。对于首次 ADD
二者冲突。仓库合同明确：首次 ADD 使用 CE pending 集合，传输确认后进入 E；
已有有效成员的目标刷新才适用 E 子集要求。原设计文档未被覆盖。

## 仍未完成的路径

1. Trainer 的 `bootstrap_and_publish`、`restore_and_publish` 仍显式失败。
   底层 CE target-only 方法存在，并不表示 TaskRunner → Trainer → CE → R/C/M 已闭环。
2. `Vpub` 不是权重快照。原生 Trainer 在本地训练后推进版本并同步；G 保护成员和同步，
   没有覆盖训练优化器更新。后续接入须选择真实同步边界，证明发送内容与版本标签一致，
   不能只把 `current_param_version` 传给 Actor 就声称重放了已发布版本。
3. 当前 `validate_server_runtime` 只接受 borrowed replica。RESTORE 还需原生 runtime
   的唤醒、装参与确认流程；不能直接复用 borrowed 健康探针伪装完成。
4. 原生 STANDALONE sleep/wake 不构成整卡释放证据。DONATE、RESTORE、FORCE 和真实
   GPU 回收须保留显式边界，经过设备验证后再开放。
5. G 内传输/服务提交异常、设备动作部分完成、Ray Actor 故障后的恢复，需要真实运行时
   验证与 owner 对账；这次单元测试不证明 CUDA/NCCL/HCCL 的清理或 GPU 独占。
